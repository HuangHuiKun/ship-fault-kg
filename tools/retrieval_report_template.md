知识版本：V4.2。复核时间：{{STAMP}}。

本报告以当前 `retrieve.py`、两份评价脚本、SQLite主数据、完整测试问题和逐题评价记录为依据。报告生成时重新执行全部62道题，与已有汇总和逐题结果逐项比较。未连接或修改Neo4j，未调用大模型，未改写原有测试结果文件。

配套文件：[62题完整检索结果与复核记录]({{AUDIT_JSON}})。其中保存每道题的输入、gold、返回事实、路径、页码、片段、得分及评价数值，方便逐项检查。

## 1. 先用大白话说明：目前到底在做什么

一句话：把“初步诊断线索”当成检索问题，先找相关历史案例或参考机理，再拿出有来源的故障事实、因果链、检查和运维建议，形成证据包，供后续报告增强使用。

比如输入“主机疑似拉缸”，程序不会直接判断这条船一定拉缸，而会找到“拉缸”参考知识单元，返回“油膜难以维持可能促成缸套黏着拉伤”等知识，附上厂家通函、物理页码、不确定性和适用机型。再把这些证据用于补充前序模型的诊断解释。

目前成果是可运行的检索与证据组织方法原型，不是训练完成的新诊断大模型。检索评价也不等于诊断准确率评价。

### 1.1 三件容易混淆的事

| 事项 | 当前真正的实现 | 不是哪种实现 |
| --- | --- | --- |
| 图谱建库与展示 | SQLite作为本地知识快照；Neo4j用于图数据库建库、查询和可视化 | 不是把Neo4j网页画出的图直接交给LLM |
| 检索 | Python读取SQLite，在内存中进行名称/别名匹配、字符TF-IDF、上下文与图路径排序 | 当前不是实时Cypher检索，也不是神经网络Embedding向量检索 |
| 报告增强 | `make_prompt()`整理证据提示词；`generate_demo.py`提供受约束的LLM证据选择与模板化草稿 | 不是大模型自由生成所有结论，也没有微调诊断大模型 |

因此：仅在Neo4j中改节点，不会自动改变当前检索结果。修改须落实到图谱源事实/规则并生成新的SQLite快照，再同步Neo4j。只运行本地检索无需启动Neo4j或Ollama。

## 2. 整个检索流程：从问题到证据包

```text
前序模型的初步诊断文本 / 手工问题
          │
          ├── 实验索引支路：识别故障名称、负载 → Run文件与行数等元数据
          │
          └── 去掉泛化问句用词 + 同义词扩展
                         │
                   名称/别名实体对齐
                         │
                三路字符TF-IDF相似度
             ┌───────────┼──────────────┐
             │           │              │
        案例/机理文档   诊断事实文档    原文片段文档
             │           │              │
      上下文加分与筛选 ───┘              │
             │                          │
      同单元因果路径搜索                 │
             │                          │
      路径优先 + 检查/措施补齐 + 事实排序 │
             │                          │
             └── 事实来源页加分 ─────────┘
                         │
             覆盖范围判断、完整路径筛选
                         │
           JSON证据包：事实 / 路径 / 出处 / 边界
                         │
          可选：提示词或LLM证据选择与报告草稿
```

### 第一步：读取输入与本地知识

入口为 `Retriever().search(query)`。命令行既可用 `--query` 输入文本，也可用 `--input-json` 读取JSON中的 `diagnosis_text` 或 `query`。

程序通过SQLite只读连接读取四张表：`nodes`、`edges`、`evidence`、`passages`。创建Retriever时重新构建内存索引，不依赖线上模型或付费接口，也没有持久化神经向量库。

默认返回上限为3个混合上下文、10条事实、4个原文片段。参数 `top_cases` 实际同时容纳历史Case和参考单元，并非只指历史事故。

### 第二步：实验数据支路先匹配故障和负载

`dataset_matches()`扫描Fault名称与别名，至少3字符的词在问题中出现时视为候选。再用正则识别40%、60%、75%、85%等负载，沿 `TESTS_FAULT` 与 `AT_LOAD` 找到Run。

返回文件名、中文运行名、负载、行数、列数、异常状态和数据来源性质。行数等来自已建库的Run属性，**不是实时重新读取原始CSV或从传感器曲线预测故障**。正则只提取第一个受支持负载；复杂区间和多负载问题目前没有通用解析。

### 第三步：去掉泛化问句词，并扩展领域词

程序会去掉“原因是什么”“为什么”“如何”“建议”“检查”等常见问句表达，减少只有问句模板也召回案例的情况。它使用字符串正则，不是完整中文分词或意图识别模型。

hybrid策略使用固定同义词规则，例如：

| 输入词 | 实际补入的相关词 |
| --- | --- |
| 烧瓦 | 轴瓦、轴承、断油、润滑油 |
| 抱轴 | 轴承、轴瓦、咬死、断油 |
| 拉缸 | 缸套、活塞、冷却、润滑 |
| 失电 | 全船失电、发电机、电力 |
| 轴带 | 轴系、联轴器、发电、推进、电机 |
| 大风浪 | 恶劣海况、纵摇、螺旋桨出水、超速 |
| CPP | 可调螺距桨、螺距控制 |

意义：不同表达能找到接近知识。局限：词表人工维护，扩展词可能偏宽；规则按原问题的子串触发，不是可训练的语义理解。

### 第四步：做名称/别名实体对齐

`entity_alignment`逐个检查Fault、Cause、Condition、Symptom、Component等节点：名称或别名是否直接出现在原始问题中。一般节点要求至少3字符，参考入口允许至少2字符；匹配到多个别名时记录最长者。

当前代码并没有训练NER模型，也未在这一支路扫描Equipment、Vessel和System类型。船名/案例名还有后续规则加分，但不能宣称已经完整实现“船舶—设备—部件—系统”的自动实体识别。代码中保留的FaultType兼容名称不意味着当前库仍有这个标签。

它能处理已登记的“烧瓦/抱轴”等别名；没有登记的术语、拼写错误、否定表达和复杂上下文需要改进。

### 第五步：三路字符TF-IDF检索

三路分别是：

1. 上下文文档：案例或参考单元的名称、别名，加上 `INVOLVES` 连接实体的名称与别名。
2. 诊断事实文档：主体名称/别名、中文关系名、客体名称/别名、上下文名。
3. 原文片段文档：片段标题，加文本前4000字符。输出摘录最多取文本前600字符，不是围绕命中词截取的窗口。

字符TF-IDF把连续中文或英文数字串切成2、3、4字符片段等，再做词频与逆文档频率加权。大白话就是：“问题与知识共有的片段越多，且这些片段在全部知识中越少见，匹配分越高。”

实际计算为：

```text
tf(t,d) = 片段t在文档d中出现次数
idf(t)  = ln[1 + (N+1)/(df(t)+1)]
w(t,d)  = [1 + ln(tf(t,d))] × idf(t)
similarity(q,d) = 查询向量与文档向量的余弦相似度
```

其中N是该路索引文档数，df是包含该片段的文档数。三路各有自己的IDF，分数不是共享的“故障概率”。这种方法比纯整词精确匹配灵活，但仍基于字符重叠；不能把它说成BGE、SentenceTransformer等深度语义模型。

### 第六步：给上下文加分，并选择候选

hybrid在上下文TF-IDF基础上叠加：

| 条件 | 加分方式 |
| --- | --- |
| 单元内实体被名称/别名匹配 | 每个命中按长度加分，单元总加分最多0.24 |
| 命中参考入口实体 | 对对应knowledge单元加0.45 |
| 问题包含上下文ID | 加1.0 |
| 问题包含完整上下文显示名 | 加0.5 |
| 命中由original_name提取的长船名词 | 加0.25；提取方式为首个空格前的词，长度至少5 |

按得分降序排序，低于0.035的单元不保留，然后截断为 `top_cases`。如果主单元是参考知识，且其入口实体被直接命中，则 `focused_reference=True`，事实范围锁定该参考单元。

这能防止“拉缸参考机理”与“另一条船主轴承事故”混成同一个根因解释。但它也使“直接输入故障名称”的测试较容易得高分。

### 第七步：寻找同一上下文里的因果路径

hybrid对排名前2个上下文分别搜索因果路径，只走 `CAUSAL_RELS` 中的边，不穿越不同case_id/knowledge_id。不把分类、检查或先后关系混作因果链。

路径搜索从各可用起点出发，避免同一路径重复访问节点，保留2～5条边的路径。每个上下文最多保留2条高分候选路径。路径分数为：

```text
路径分 = 路径中各边的事实TF-IDF分之和 / √边数
       + 0.25 × 上下文分
       + 0.018 × min(边数,5)
```

这是一套人工设计的启发式排序，不是训练出来的图神经网络。长度奖励有利于保留完整解释，但也可能更偏好长链，不代表长链就更可靠。

### 第八步：组织最终事实，而不只是机械取Top-K

普通候选事实的综合分为：

```text
事实综合分 = 0.68 × 事实TF-IDF分 + 0.32 × 所属上下文分
```

最终列表还执行结构性优先规则：

1. 先放入主单元排名第1的整条因果路径。
2. 尝试补入主单元最相关的1条CHECKS检查关系。
3. 尝试补入主单元最相关的1条ADDRESSES或PROMPTS措施关系。
4. 按综合分补足候选上下文中的其余事实，按边ID去重，截断至 `top_facts`。

所以实际事实列表不是严格按显示score从大到小排列；路径和检查/措施可能被优先返回。这也是Recall和Precision受影响的原因：前5条可能既有链条又有检查、措施，而gold只标了其中部分。

最后只展示所有边都在最终事实列表中的完整路径。不完整的候选链会被隐藏，而不是凭空补出缺失边。当前没有训练式Cross-Encoder重排模型或RRF融合算法。

### 第九步：补来源片段，并判断证据覆盖范围

片段基础分来自TF-IDF；若其“文件+页码”正好是已选事实的来源页，则加0.3，再选择默认最多4个正分片段。片段从全局检索，不完全限制在主上下文；因此其他机理/语料片段可能出现，不能一律当成所选案例的直接证据。

事实本身则从 `evidence_id` 读取来源文件、物理页、URL和原文证据。因果解释应优先绑定这些事实对应的出处，不能只依赖任意高分文本。

特别是中文问题与英文PDF页，字符相似度可能很低。实际例子中出现多个0.3分片段，主要是来源页加分在起作用，不代表已经实现跨语言深度语义匹配。

| coverage状态 | 意义 | 下游应如何使用 |
| --- | --- | --- |
| case_evidence | 找到相关历史案例 | 作为历史参照，仍须验证本船 |
| reference_knowledge | 找到厂家机理、论文观察或报告参考单元 | 补充解释与待检查项，保留适用范围 |
| related_cases_only | 只有相邻系统案例，没有相应直接案例/参考入口 | 不能宣称找到直接根因 |
| dataset_metadata_only | 仅实验工况元数据达到使用条件 | 只能说明文件和工况，不推断事故根因 |
| no_evidence | 没有足够相关上下文或实验匹配 | 清空事实、路径、片段并提示补资料 |

这些状态由规则判断，而非统计校准过的置信度。边的 `certainty=probable` 表示来源“很可能”的措辞，不是模型算出了某个概率。

## 3. 检索结果到底是什么样

返回结果是JSON证据包，不是最终确诊结论。主要字段如下：

| 字段 | 用大白话解释 |
| --- | --- |
| query | 原始诊断线索或问题 |
| primary_context | 本次最高分的案例或参考单元 |
| coverage / coverage_warning | 有什么证据、缺什么、不能推出什么 |
| entity_alignment | 命中的实体ID、类型、显示名和名称/别名 |
| dataset_matches | 故障试验文件、负载、行数等 |
| cases | 历史案例候选列表 |
| knowledge_units | 参考机理候选列表及适用范围 |
| causal_paths | 同一单元内部、完整保留的因果链及边ID |
| facts | 主体—关系—客体、确定性、分数、出处和原文证据 |
| passages | 返回原文片段的文件、页、URL、分数及摘录 |
| retrieval_method / retrieval_strategy | 使用hybrid还是字符检索基线 |

单条fact还有 `context_role`、`context_kind`、`applicability` 等字段。即使Fault入口类型与普通故障相同，也能区分“参考知识”与“历史案例事实”。

## 7. 指标是什么、怎么算：按当前代码逐项解释

### 7.1 先明确计算对象

| 名词 | 含义 |
| --- | --- |
| query | 一道输入问题 |
| gold / 标准答案 | 开发者人工指定的目标单元或事实集合；不是LLM自动判出的答案 |
| Top-K | 最终返回列表的前K条；当前有路径/检查/措施优先规则 |
| hit / 命中 | 返回项按当前评价规则与gold完全匹配 |
| rank | 目标单元在返回候选列表中的名次，从1开始 |

当前没有“相似度超过多少就算gold”的宽松判断，也没有调用LLM裁判。事实名称改写要先映射当前显示名；稳定ID组则按ID匹配。

### 7.2 Recall@K：该找到的，找回来多少

```text
Recall@K(q) = 前K条中命中的不同gold事实数 / 本题gold事实总数
```

大白话：标准答案有3条，前5条拿回来2条，就召回了2/3=66.67%。两组汇总均按题分别计算，再做算术平均，即宏平均，不是把所有命中数除以所有gold数的微平均。

实现细节：案例组用集合交集计算命中数，重复三元组只算一次；参考组逐条判断返回三元组是否属于gold。当前参考题没有重复命中三元组，因此可按上述公式理解；未来若增加相同三元组的多来源平行边，应先去重，避免重复计数抬高Recall。

### 7.3 Precision@K：前K条有多少被算成正确

概念上看的是返回结果的精度，但当前两组代码采用不同口径：

```text
38题组中的33道案例题：
Precision@5(q) = 前5条命中的不同gold事实数 / 5

24题参考故障组：
Precision@K(q) = 前K条命中gold的条数 / min(K, 实际返回事实条数)
若没有返回事实，取0
```

因此参考题只返回7条且都属于gold时，Precision@10=7/7=100%，不是7/10=70%。案例题只有3条gold，即使前5条已返回全部3条，Precision@5也最多60%；Q02只有2条gold，最高40%。这与“额外返回的图谱事实是否真实、有用”不是同一件事。

在案例组里，未列入本题gold的事实都会被视为未命中，其中可能包含真实的其他因果边、检查或运维建议。当前43.64%不能直接解释成“56.36%的返回事实错误”。它也反映gold不完整和固定分母的影响。

### 7.5 用“拉缸”参考题演算

拉缸单元共7条gold。前5条命中5条，所以Recall@5=5/7=71.43%，Precision@5=5/5=100%。前10实际返回7条、命中7条，所以Recall@10=7/7=100%，Precision@10=7/7=100%。

这说明“返回的都在该参考单元gold里”；不代表该7条都是本船的已证实根因，也不代表本模型能正确诊断所有拉缸问题。

### 7.6 MRR@3：正确单元排得靠不靠前

```text
RR(q) = 1 / 正确目标首次出现的名次
若目标不在返回列表中，RR(q)=0
MRR@3 = 所有适用问题RR的算术平均
```

第1名为1，第2名为0.5，第3名约0.333，未检索到为0。MRR不是“有多少事实正确”，也不是“回答准确率”。

当前默认总共截断3个混合上下文；随后返回时分开为 `cases` 和 `knowledge_units`。案例MRR在过滤后的历史案例列表算，参考MRR在过滤后的参考单元列表算。因此它不是统一的31个上下文混合排名评价；若另一个类型的单元排在更前，过滤后名次会变化。后续应同时评价 `primary_context` 和混合排名，以判断真正首选单元是否正确。

`case_recall_at_1`在当前每题只有一个目标案例的条件下，统计历史案例列表第1名是否正确，等价于该口径的Top-1命中率。这个实现不能直接推广为多目标Recall@1。

### 7.7 另外两个指标

**实验索引准确率**：Q10和Q11中，是否存在某条返回记录，其 `run_file` 与指定路径完全相同，且 `data_rows` 与5845/5801一致。命中题数/2。未评分额外错误文件、排序、时间序列异常检测或故障分类性能。

**覆盖状态准确率**：Q12、NEG1、NEG2的返回 `coverage` 字符串是否与标签一致。正确题数/3。只评价状态标签，不评价提醒文字是否完整，更不代表对所有范围外问题可靠拒答。

## 9. 如何与LLM及师兄的模型衔接

推荐接口：师兄模型输出设备/部件、异常表现、工况、候选故障和不确定性；将这些整理为 `diagnosis_text` 输入本检索器；检索器输出证据包，补充解释、检查依据、可参考措施与来源。

### 9.1 两个现有入口要分清

`retrieve.py --prompt`：调用 `make_prompt(result)`，把诊断线索、覆盖提醒、实验索引、事实编号、来源页码、适用范围和最多3条完整路径整理成提示词。**这个入口只打印提示词，不调用LLM。**

`generate_demo.py`：当前实际演示是让本地Ollama中的 `qwen2.5:3b-instruct`从已返回事实中选择编号，输出fault_chain、checks、actions三类JSON；程序检查编号有效性、关系类型和主上下文，必要时用图谱事实补齐；最后由代码模板组织带引用的中文草稿。不是让LLM无约束地编写全部正文。

当前报告生成没有运行Ollama，所以这里说明的是已有代码机制，不宣称本次重新验证了大模型效果。38题和24题的评价只检索知识，不评价LLM正文、引用忠实性或运维建议安全性。

### 9.2 衔接时应明确分工

| 上游/本模块/下游 | 输入或输出 | 本模块边界 |
| --- | --- | --- |
| 师兄的前序诊断模型 | 原始信号分析后的初步诊断线索 | 本模块不重新训练信号诊断模型 |
| 本模块实体与知识检索 | 目标单元、事实、因果链、证据 | 基于现有知识，不把历史例子当本船结论 |
| 报告增强 | 故障假设、因果解释、待检查项、参考措施、引用 | 专业人员复核，保留不确定性与适用边界 |
| 后续评价反馈 | 哪些证据不足、哪些判断需修改 | 反馈闭环仍需联调，当前不是完整自动闭环 |

一个适合组会的表述是：“前面的模型告诉我设备可能出了什么问题，我这一块负责查图谱，把为什么可能出问题、还要查什么、哪些建议有依据和依据来自哪里补完整。现在已跑通本地检索和开发测试，后面要做独立标注与真实诊断报告联调。”

## 10. 当前局限与下一步如何优化

| 当前问题 | 为什么重要 | 可执行的下一步 |
| --- | --- | --- |
| 没有独立专家测试集 | 同源题、名称提示和规则加分容易高估效果 | 从未参与构图的真实报告建立独立查询集，由专家标实体、事实、路径和适用范围 |
| 案例gold只有2～3条 | 真正相关但未标注的事实被当成未命中 | 补完整、按具体问题标注相关性等级，并记录争议事实 |
| 两组Precision口径不同 | 容易误读43.64%与100% | 统一报告固定K和实际返回分母两种口径；增加逐题返回长度 |
| MRR在分类型列表计算 | 无法完整评价混合上下文首选 | 增加混合rank、primary_context命中率，以及案例/机理误分类统计 |
| 字符TF-IDF语义能力有限 | 同义词、否定、单位、缩写、新表达可能漏召回 | 建专业术语词典；加入设备/系统约束、否定识别；再对比中文领域Embedding、BM25等候选方法 |
| 没有完整Equipment/System实体识别 | 输入中的设备构型约束利用不足 | 扩展对齐类型，处理同名不同案例实体，显式解析工况与机型 |
| 路径优先可能挤占前K事实 | 有利于连贯解释，但可能漏指定检查项 | 按问题意图分配因果/检查/措施配额；对权重与K做消融实验 |
| 原文片段可能跨单元漂移 | 高分文本不一定是同一案例证据 | 加上下文/来源约束、候选片段去重、命中窗口摘录，评价出处一致性 |
| 12个记录级Source未建独立检索通道 | 有节点不等于监测汇总已被充分检索利用 | 设计状态—记录—建议检索支路，并建立对应gold问题 |
| 缺少路径级与输出质量评价 | 当前事实召回不等于完整因果链正确 | 增加路径完整命中、因果/相关区分、引用页码正确率、解释忠实性和专业安全性评价 |
| 阈值和覆盖判断是规则 | 两个负例不足以保证可靠拒答 | 加入难负例、近似故障、无直接证据及多故障混合问题，调校拒答条件 |

本报告只指出改进项，不修改当前检索逻辑，也不把尚未实现的Embedding、BM25、Cross-Encoder或反馈闭环描述为已完成。

### 10.1 推荐的实验顺序

1. 冻结一份当前SQLite快照，记录版本和SHA256；固定独立测试题与标注。
2. 先测当前hybrid，再测 `lexical` 基线，记录单元定位、事实召回与路径完整性。
3. 分别关闭同义词、实体加分、路径优先、检查/措施优先等规则做消融，判断每一步是否真的有用。
4. 再引入新的语义召回或重排方法；在同一gold、同一K、同一数据版本上比较。
5. 与真实前序诊断结果联调，单独评价最终增强报告，不用检索指标代替诊断指标。

注意 `lexical` 也不是完全无规则的全局纯TF-IDF：当前代码仍使用候选上下文范围和显式ID/名称规则，片段仍可按证据页加分，而且输出fact的score字段仍用混合公式。做严格消融时应记录实际开关与排序依据，不能只凭策略名字判断方法差异。
