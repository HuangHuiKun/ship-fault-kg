# 与上游混合智能诊断模型的接口对接说明

版本：候选接口 v1.0；日期：2026-10-12。本文与100份合成初始报告配套，可直接作为双方讨论字段的底稿。

## 1. 四项核心输出如何承接

| 师兄负责的输出 | 本模板字段 | 你的模块如何使用 |
| --- | --- | --- |
| 深度学习诊断结果的文本化 | `diagnosis.summary`、`diagnosis.candidates` | 识别故障、设备、异常状态及否定；保留原始判断 |
| 关键物理量与中间层预测 | `physical_quantities`、`operating_context` | 按设备/工况检索；将观测和预测分开；核对单位与缺失 |
| 随机性约束的诊断置信度 | `diagnosis.confidence` | 原样承接计算方法、分数、对象、分布和校准状态 |
| 初步故障溯源与固定格式报告 | `observations`、`initial_evidence_chain`、`initial_trace_text` | 接着检索参考机理、检查依据、措施和出处，形成追加内容 |

师兄仍负责诊断文本、物理量、置信度和初步溯源。你负责知识检索和证据约束下的解释增强。检索命中不能自动证明上游故障正确，也不能默认修正上游模型分数。

## 2. 建议共同确认的字段规则

- 报告必须有唯一 `report_id`，能够回溯到模型版本、输入信号及观测时间窗口。
- 设备具体型号与工况未知时填 `null` 或明确状态，不能只凭设备名称假定某厂机型。
- `channel_role=observed` 表示观测通道；`predicted` 表示中间层物理量预测；派生特征另用 `derived`。
- 当前值、同工况比较基线、适用厂家阈值是三个不同字段。本批厂家阈值均为空。
- 缺失数值用 `null`，不能用0代替。某些反馈的真实0值有意义，不能自动转成缺失。
- 故障候选状态保留疑似、未观察到、信息不足等语义；初始报告不默认填写已确认根因。
- `confidence.target` 明确分数对应候选故障、异常识别还是当前正常状态。不同对象的分数不能直接比较。
- `confidence.method`、`method_version`、`stochastic_constraint_result`、`prediction_distribution` 留给师兄真实方法。本批均明确为人工设定或空值。
- 只有在模型本身提供概率解释和校准依据时，才能把分数表述为校准概率。
- 上游初始证据链对应观测/预测到初步判断；知识图谱因果路径由后续模块提供，二者分开存储。

## 3. 当前数据怎样送入检索器

`initial_reports.jsonl` 保留完整结构化报告。`retrieval_inputs.jsonl` 是其中可直接送入当前检索器的文本版本，每行只有：

```json
{"report_id":"DR-001","diagnosis_text":"设备、工况、初步诊断、物理量、模型分数及检索目标……"}
```

参考标注通过 `report_id` 在评测端关联。不要把 `retrieval_reference_labels.jsonl` 的目标ID、来源、原文、路径或声明集合拼入输入，这会提前泄露答案。

本批对40个基础场景各提供两种报告：明确候选名称、只有症状。二者物理量完全相同，可检查去掉故障词后，召回是否仍能覆盖相同的参考知识。两种报告的分数评价对象不同，不能把它们当作同一根因置信度的受控对比。

## 4. 知识增强报告建议追加什么

下列是后续输出接口草案，本批未伪造这些结果：

```json
{
  "upstream_report_id": "DR-001",
  "upstream_diagnosis_preserved": true,
  "reference_mechanisms": [],
  "conditional_causal_paths": [],
  "discriminating_checks": [],
  "reference_actions": [],
  "citations": [],
  "applicability_and_conflicts": [],
  "remaining_evidence_gaps": [],
  "diagnostic_confidence_update": null
}
```

每条追加事实至少保存声明ID、来源、位置、原文、确定性与适用范围。路径逐边保持方向及范围；跨资料仅能作为多个参考解释，不能默认为同一条已证实事故链。检查与措施缺少依据时标为缺口，不为凑齐模板补编。

`diagnostic_confidence_update` 暂留空。如果未来需要根据新证据更新置信度，应另外定义并验证更新方法，保留原始分数、更新后的对象、方法和依据。

## 5. 接下来可直接开展的工作

1. 用60份开发输入调试设备/症状识别、否定保留和证据筛选；40份检查输入用于阶段回归。
2. 把38份可按Fault候选计分的明确名称报告，与38份症状报告逐对比较；另有2个State目标场景，需要单独评价状态入口。
3. 对20份边界报告检查：是否保留否定、是否编造缺失值、是否过早选定唯一根因、是否无厂家资料却生成精确参数。
4. 选取代表性报告，与师兄共同确认字段含义，之后把合成数据替换为他的仿真模型输出。
5. 后续取得真实报告后重新标注相关证据和备选解释，另设独立测试集。本批来源和表述仍有重叠，仅用作开发起步。

## 6. 当前交付的验证范围

已经自动核对：报告结构、数量、分区、配对物理量、数值趋势、来源指纹、引用片段、路径方向和同范围约束。诊断场景及数值为助手构造，尚无船舶领域专家复核；模板也尚未对照船级社术语文件确认。
