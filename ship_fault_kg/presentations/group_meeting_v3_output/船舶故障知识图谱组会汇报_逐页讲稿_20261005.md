# 船舶故障知识图谱构建与RAG增强诊断：组会讲稿

汇报人：黄辉坤。配套10页PPT，建议按约7～10分钟练习。PPT每页备注区也有口语化讲稿及资料引用。

## 开场几句话

这段时间，我先搜寻了船舶相关的知识图谱。虽然找到了相关论文和代码，但在已调研范围内，还没有找到能直接下载复用、又满足我们诊断增强需求的完整图谱，所以选择自己搭建。

随后，我下载了船舶故障数据集、官方事故报告和厂家技术资料，以这些材料作为事实和溯源依据，构建了一个以故障为入口的知识图谱，并完成了Neo4j建库和可视化。

接下来，我会一边根据真实资料优化图谱，一边做检索和报告增强实验，接收师兄模型输出的初步诊断结果，补充机理解释、检查与运维建议，以及来源证据。

## 第1页：研究任务

各位老师、师兄好。我今天汇报的是船舶动力系统故障知识图谱的构建进展，以及后续怎样利用这个图谱增强诊断报告。我负责的重点是承接前面模型给出的初步诊断结果，为它补充故障机理、检查和运维建议，以及能查到原文的来源证据。

## 第2页：阶段工作总结

这一页可以直接使用上面的开场总结。重点说清楚四件事：调研后决定自建、找到可溯源资料、完成建库与展示、下一步接入诊断结果开展RAG实验。

这里的“没有找到”是指没有找到满足当前需求、可直接复用的完整图谱，并不是说船舶知识图谱研究不存在。

## 第3页：资料来源与用途

资料主要分为几类。第一类是四个公开数据集，包括实机柴油机故障试验、中文船机语料、推进器状态监测和推进仿真资料，它们提供故障标签、测点和工况。

第二类是MAIB官方事故调查报告，主要提供事故原因、经过、后果和建议。第三类是制造商资料，本轮新下载16份PDF，其中15份实际支持新增结构化事实，另一份保留为参考文本。第四类是论文和代码，用来参考图谱模式、信息抽取、因果路径检索和评价方法。

需要说明的是：下载资料没有全部转成图谱，仿真数据没有冒充实船事故，参考开源代码也不代表已经集成了其中所有算法。

具体资料举例：

- 数据：Marine Engine Fault Dataset、Marine diesel RAG corpus、Azimuth Thruster CBM Dataset、UCI Naval Propulsion CBM。
- 报告：Wight Sky、Windcat 8、Kommandor Susan、Queen Mary 2、Pride of Canterbury等MAIB报告。
- 技术资料：MAN拉缸、气缸润滑、轴承磨损监测、冷却水与减振器通函，STAMFORD/AvK轴带发电、轴承电流、绝缘和扭振资料。
- 方法参考：船用柴油机故障知识图谱论文，HFACS-KG、TSRF和弱热故障诊断代码。代码以参考为主。

## 第4页：构建与审核

构建过程不是直接让大模型凭空生成一张图。首先确定船舶、设备、部件、故障和原因等实体，以及它们之间有哪些关系。

然后按原文页码核对，把复杂段落拆成可审核的事实。例如，资料说油膜受损“可能”造成拉缸，我就保留这个可能性，不改成确定结论。

接着给实体设置稳定ID，整理重复项，同时给每条关系标注它属于哪起事故或哪一个文献机理单元，避免不同案例拼出一条假的因果链。

最后生成SQLite主数据，包含实体、关系、证据和文本片段四张表。当前296个来源定位锚点检查通过，但定位正确仍不能替代专家对工程机理的审核。

## 第5页：故障覆盖

现在图谱覆盖燃油进排气、润滑轴承、冷却海水、传动推进和电力控制五个功能子系统。本轮补充了拉缸、烧瓦、轴承电蚀、轴带对中异常和电网振荡等经典知识，形成12个参考入口，同时保留19起历史事故。

一个故障可以同时涉及热、机械和电气。例如齿轮箱热膨胀影响对中，再影响轴带发电机振动。

这里的12个入口不是12起新增事故。联轴器的事故证据目前是CPP执行器小联轴器失效，不能说已经建立大型船主轴联轴器断裂的真实事故链。

## 第6页：实体、关系与证据

可以把图谱理解成一个能沿关系查证据的知识网络。它有20类实体，包括船舶、设备、部件、故障、原因、症状、检查和措施，还有案例、来源和实验数据。32类关系里只有部分是因果关系，归属和分类关系不能当成机理结论。

拉缸示例返回7条诊断关系和9个实体。核心路径是：缸套表面抛光或涂抹促成油膜难以维持，油膜问题可能促成黏着拉伤，拉伤导致表面硬化需要修复。图谱还连接了缸况检查和厂家处理建议。

每条边保留来源文件、原文、物理页码和适用机型。后续报告中的解释和建议可以引用这些字段。

## 第7页：Neo4j建库与可视化

我把SQLite里的实体和关系直接生成Neo4j的MERGE和SET语句，通过已经登录的Browser导入shipfaultkg数据库，不需要先转CSV。节点使用稳定ID，并设置唯一约束，方便后续增量更新。

导入后重新查询实际数据库，现在是500个活动节点、1201条活动关系，15个核心测点、12个故障参考入口和19起事故。332条证据和852个文本片段是SQLite主数据里的数量，不能说全部来自截图上的数据库统计。

可视化显示中文实体名和关系名，按故障查看比一次显示所有边更直观。55个非核心测点和86条关系只是归档，仍能恢复，原始文件没有删除。

## 第8页：增强报告原型

图谱建好后，我已经跑通一个报告增强原型。输入“主机疑似拉缸”，检索得到这个参考单元里的7条事实。大模型选择用于解释、检查和措施的证据编号，程序再核查编号和上下文，最后按约束模板输出带页码引用的草稿。

目前证明的是检索到报告的流程可以运行，还没有证明真实诊断准确率。检索用了实体别名、关键词、字符TF-IDF相似度和图关系补全，尚未接入神经向量模型和学习式重排序器。

24道题属于开发自测，不能把结果当成独立专家测试，也不能把检索准确率当成诊断准确率。

## 第9页：与师兄模块衔接

前面的诊断模块先根据运行数据和模型，给出设备、症状和候选故障等初步判断。我接收这个结果，识别和对齐实体，再检索相关原因、因果路径、检查方法和运维措施。

检索结果融合排序后形成Evidence Pack，也就是带来源的证据包，再引导大模型生成增强报告。报告要说明为什么这样判断，有什么检查和建议，依据哪份资料，以及哪里仍不确定。

最后与评价模块衔接，根据反馈补检索或修改报告。目前这是拟定接口方案，还需要和师兄共同确定诊断字段及设备构型信息，尚未完成真实数据联调。

这部分的主要交付是**知识图谱、检索增强方法、报告生成原型和实验结果**。当前使用已有大模型，不涉及从头训练一个新的故障识别模型。

## 第10页：下一步计划

后续两条线并行。第一条线持续优化图谱，拿到真实船舶资料后修订实体、关系和适用机型，并记录每次变更。

第二条线开展RAG实验。先建立独立标注集，明确哪些实体、事实和路径应当检索到，再用Recall@K、Precision@K和MRR优化召回与排序。之后比较同一批输入下，不检索、普通文本RAG和图谱增强报告的差别，重点看证据一致性、解释合理性、遗漏和幻觉。

最后接入师兄的标准化初步诊断和评价反馈，形成端到端增强报告。近期最需要的是初步诊断输入样例和专家审核。真实电网测点及主轴断裂事故证据也仍需补充。

## 组会上可能被问到的问题

**最终交付是训练模型还是一套方法？**

当前交付是知识图谱及配套检索增强方法、原型系统和实验结果。已有模型负责初步诊断，我这部分补充知识、解释和来源。若以后需要微调，要另设研究目标和实验，不能算作目前已完成内容。

**有图谱为什么还要大模型？**

图谱保存可核查的知识和关系，大模型把检索出的证据组织成自然语言报告。两者配合后，既能输出比较容易读懂的解释，也能提供来源。仍需程序校验和专业审核。

**与普通文本RAG的区别是什么？**

文本RAG主要返回相似段落，图谱增强还能够显式检索设备、故障、原因与检查措施之间的关系，并按同一事故或机理单元约束路径。是否真正更好，需要在相同输入、模型和评价集上开展对照及消融实验。

**是否已训练实体识别或语义检索模型？**

没有。当前先采用别名匹配和字符TF-IDF等轻量方法跑通流程。后续拟加入向量语义检索与重排序，再与现有策略比较。

**1201条关系是否都是因果关系？**

不是。包含归属、分类、设备结构、实验数据和来源关系。当前244条属于诊断关系，其中133条属于因果类关系，不应把组织关系算成故障机理。

## 汇报时可运行的Neo4j查询

先连接`http://localhost:7475/browser/`，选中`shipfaultkg`。逐段运行，不要一次粘贴所有查询。

故障入口总览：

```cypher
MATCH (f:ShipKG:FaultType)-[r:IN_SUBSYSTEM]->(s:ShipKG:Subsystem)
RETURN f,r,s;
```

拉缸诊断关系：

```cypher
MATCH (a:ShipKG)-[r]->(b:ShipKG)
WHERE r.case_id='knowledge:liner_scuffing'
  AND type(r) IN ['CONTRIBUTED_TO','MAY_CONTRIBUTE_TO','LEADS_TO',
                 'CHECKS','ADDRESSES','INDICATES']
RETURN a,r,b;
```

来源证据表：

```cypher
MATCH (a:ShipKG)-[r]->(b:ShipKG)
WHERE r.case_id='knowledge:liner_scuffing' AND r.knowledge_layer='reference'
RETURN a.name,r.name,b.name,r.certainty_zh,r.applicability,
       r.source_file,r.page,r.quote,r.source_url;
```

返回节点和关系才能看到Graph。返回字符串、数量或来源字段时看Table。完整查询见[queries_v3.cypher](D:/RAGQnASystem/RAGQnASystem-main/ship_fault_kg/queries_v3.cypher)。
